}

# 项目背景与痛点

当前存在项目 A、B、C 三个独立项目，它们面临以下问题：

1. **代码重复严重**：三个项目之间存在大量相似的 API 接口调用逻辑，每个项目都在重复实现相同的功能
2. **接口差异管理困难**：接口的请求参数和返回数据结构略有差异，但核心业务逻辑高度一致
3. **维护成本高**：缺乏统一的数据转换、错误处理、拦截机制以及其他通用能力
4. **缺乏标准化**：没有统一的接口管理、版本控制和文档化机制

# 核心目标

设计并规划一个**可复用的 API Hooks 库**，使其能够：
- 在多个项目（A、B、C）中直接复用
- 减少重复劳动，降低相同类型项目的落地时间
- 提高开发效率和代码质量

# 核心功能需求

## 1. 统一 API 管理

- 将通用接口定义集中在独立的库中进行统一管理
- 支持接口的版本控制和文档化
- 提供清晰的接口分类和命名规范
- 支持接口元数据管理（如接口描述、参数说明、返回值说明等）

## 2. React Hooks 生成

- 为 React 项目提供开箱即用的 Hooks 调用方式
- **不内置**任何 HTTP 请求库（如 axios、fetch 等）
- 支持项目自行引入请求库（例如 umi 的 request 库、axios、fetch 等）
- 通过**插件注入**或**适配器模式**的方式集成项目的请求库
- 生成的 Hooks 应支持常见的状态管理（loading、error、data 等）

## 3. 灵活的扩展机制

- 支持自定义响应数据转换逻辑
- 提供统一的错误处理和错误边界
- 支持中间件/拦截器模式进行功能扩展（如请求拦截、响应拦截、日志记录、性能监控等）
- 支持插件化架构，允许开发者自定义扩展功能

## 4. DTO → VO 转换机制

- 提供统一的后端数据传输对象（DTO）到前端视图模型（VO）的映射机制
- 支持类型安全的数据转换，充分利用 TypeScript 类型推导
- 支持字段重命名、数据格式化、默认值处理、字段过滤等常见转换场景
- 支持自定义转换器，支持转换器的链式调用和组合
- 支持转换器的复用和继承

## 5. Headless 调用支持（框架解耦）

- **核心架构要求**：核心逻辑层（Core Layer）必须与 React 框架完全解耦
- Core 层实现所有通用逻辑（请求管理、数据转换、错误处理、缓存、重试等），不依赖任何 UI 框架
- Core 层可以单独作为独立的 npm 包使用
- React 层仅作为适配层，提供便捷的 Hooks 调用方式
- 支持在非 React 上下文中直接调用核心 API 方法（例如在普通 TypeScript 文件）

# 设计约束条件

1. **可维护性优先**：代码结构清晰，职责分离明确，模块边界清晰，易于后续迭代和扩展
2. **简洁性原则**：避免过度设计，API 设计应简洁直观，学习成本低
3. **开发者体验**：学习曲线平缓，文档完善，IDE 类型提示友好，错误提示清晰
4. **类型安全**：充分利用 TypeScript 的类型系统，提供完整的类型推导和类型检查，减少运行时错误
